# 本轮优化记录（内核驱动 + Python 客户端）

本文档记录对 `kernel/vcan_usb`、`kernel/vkgs_usb`、`python-cli/vcan_usb`、
`python-cli/vkgs_usb` 及配套测试/文档做的一轮系统性优化：可读性、稳定性、
功能补全、宏/命名规范、测试与驱动文件分离。原有功能全部保留，**新增了几项
用户可见的行为**，已在下面逐条标出，避免误以为是纯重构。

验证方式：内核驱动在本机实际 `make` 编译通过（有匹配的 6.8.0-136-generic
内核头），但本环境未接入真实硬件，`kernel/tests/*/test_*.sh` 需要用户自行
在有设备的机器上跑；Python 侧改动跑通了 `tests/unit` 全部 26 个用例
（`python -m unittest discover -s tests/unit -v`）。

---

## 一、内核驱动（`kernel/vcan_usb`、`kernel/vkgs_usb`）

### 1. 新增功能（用户可见行为变化）

- **`berr-reporting` 开关正式打通**（此前完全未接线）。两个驱动现在都会：
  - 在探测阶段根据固件上报的 feature 位，把 `CAN_CTRLMODE_BERR_REPORTING`
    加入 `ctrlmode_supported`；
  - 收到 `ip link set canX type can berr-reporting on` 后，向固件下发
    `MODE_BERR_REPORTING` 标志位；
  - 打开后，收到的 BERR 事件帧会被解码为标准 `CAN_ERR_PROT_*`（stuff/form/
    ACK/bit0/bit1/CRC）错误帧并推给 SocketCAN；关闭时仍和以前一样，只更新
    `rx_error_count`/`tx_error_count` 计数缓存，不产生错误帧。
  - 总线状态帧（bus-off / error-passive / error-warning）的上报**没有变化**
    ——那部分本来就与这个开关无关，一直是打开的。
  - `vcan_usb.h` 补上了此前遗漏的 `VCAN_USB_FEATURE_BERR_REPORTING`(bit12)、
    `VCAN_USB_FEATURE_GET_STATE`(bit13) 定义（`vkgs_usb.h` 已有对应定义）。

- **`vkgs_usb` 新增 identify/blink LED**，通过标准 `ethtool -p canX <秒数>`
  触发，内部走固件的 `VKGS_USB_BREQ_IDENTIFY`(7) 请求。固件收到 mode=1 后自行
  控制 LED 闪烁节奏，驱动只负责发起/停止。
  **`vcan_usb` 没有做这个** —— 核实过 `hal_vcan_reg.h` 虽然声明了
  `HAL_VCAN_USB_FEATURE_IDENTIFY` 这个 feature 位，但 `hal_vcan_frame.c`
  里根本没有任何 `case ...IDENTIFY` 处理（VCAN 协议的请求枚举里没有这个
  请求号），说明这个 feature 位在当前固件里是遗留声明、并未真正实现。驱动侧
  接了也没用，所以没接。见《[驱动特殊API说明](驱动特殊API说明.md)》里的
  说明。

- 其余固件里有但驱动/Python 都没用到的能力（硬件 RX 滤波表、
  `GET/SET_USER_ID`、`TIMESTAMP`、`USB_MODE` 持久切换）**保持不动**——
  `USB_MODE` 切换已经由 `python-cli` 的 `switch_usb_mode()` 覆盖，
  `GET_USER_ID` 在 gs_can 固件里本身标注"not implemented"，硬件滤波表按软件
  过滤 + 交给上位机管理的既有设计，没有必要在内核层重复实现。

### 2. 稳定性

- `do_get_berr_counter()`（两个驱动）不再每次都发一次同步 USB 控制传输去读
  设备状态——直接返回已经被 RX 路径上的 STATE/BERR 事件帧持续更新的
  `dev->bec` 缓存。避免 `ip -details -statistics link show` 频繁轮询时引入
  额外的 USB 往返延迟；行为上完全等价，因为缓存值本来就是最新的。
- `vkgs_usb_set_bittiming()`/`vkgs_usb_set_data_bittiming()` 里的位时序结构体
  改成显式 `= { 0 }` 零初始化，与 `vcan_usb` 侧保持一致（字段本来就会被
  全部填充，纯风格统一，不是 bug 修复）。

### 3. 宏/命名规范

- `HAL_VCAN_USB_BREQ_BSP_DEVICE_INFO` → `VCAN_USB_BREQ_BSP_DEVICE_INFO`，
  `GS_USB_BREQ_GET_BSP_DEVICE_INFO` → `VKGS_USB_BREQ_BSP_DEVICE_INFO`
  （去掉泄漏进来的固件内部 `HAL_`/`GS_USB_` 前缀，统一成各自驱动自己的
  `VCAN_USB_*`/`VKGS_USB_*` 命名空间）。
- `VCAN_USB_MODE_PAD_PKTS` → `VCAN_USB_MODE_PAD_PKTS_TO_MAX`，与
  `vkgs_usb.h` 里的 `VKGS_USB_MODE_PAD_PKTS_TO_MAX` 对齐。
- 新增 `vcan_usb_error_code`/`vkgs_usb_error_code` 枚举（stuff/form/ack/
  bit1/bit0/crc），供 BERR 事件帧解码使用，两个驱动数值一致（共享同一份
  固件内部 `hal_can_error_code_t`）。
- 以上重命名均已同步更新到对应 `README.md` 里的旧引用（此前 README 里部分
  引用的宏名其实和代码里已经不一致，顺带修正）。

### 4. 测试/驱动文件分离

- `test_vcan_usb.sh`、`test_vkgs_usb.sh` 从 `kernel/vcan_usb/`、
  `kernel/vkgs_usb/`（DKMS 打包源码目录）移到新建的 `kernel/tests/vcan_usb/`、
  `kernel/tests/vkgs_usb/`，与 `python-cli/tests/` 的顶层测试目录风格保持
  一致。DKMS 源码目录现在只剩 `*.c`/`*.h`/`Makefile`/`dkms.conf`/`README.md`。
  脚本内部的 `cd`/`make`/`insmod` 相对路径已同步改成指向驱动源码目录，脚本
  可以从任意位置以 `.../kernel/tests/<driver>/test_*.sh` 调用。
- 内核 `.c` 文件里没有发现遗留的调试 `printk`/`#if 0` —— 现有调试输出全部是
  `dev_dbg`/`netdev_dbg`，走 kernel dynamic debug 机制（默认不打印），本来
  就是正确做法，未改动。

## 二、Python 客户端（`python-cli/vcan_usb`、`python-cli/vkgs_usb`）

两个包保持各自独立可安装（未合并成公共包），`bus.py`/`transport.py`/
`winusb.py` 的整包复制按原样保留；改动集中在 `protocol.py`、`bus.py` 的少量
新增方法，以及测试文件组织。

### 1. 新增功能（用户可见行为变化）

- **`bus.state` 现在会真实反映总线状态**，此前两个包的 `parse_bulk()` 都会
  把 STATE/BERR 事件帧的内容直接丢弃（`vkgs_usb` 甚至连字段布局都解析错了,
  只是恰好没人用到），`bus.state` 因此永远是 python-can 默认值 `ACTIVE`。
  现在会正确解码并缓存，`bus.state` 在控制器进入 error-passive/bus-off 时
  返回 `can.BusState.PASSIVE`（python-can 的 `BusState` 只有
  `ACTIVE`/`PASSIVE` 两档，error-warning 仍归入 `ACTIVE`）。
- 新增 `bus.get_berr_counter()`，返回最近一次上报的
  `{"rxerr": ..., "txerr": ...}`，比 `state` 的两档模型更细，来源于 STATE/
  BERR 事件帧的被动更新，不产生额外 USB 流量。
- **`vkgs_usb` 新增 `bus.identify(enabled=True)`**，对应内核驱动新增的
  identify/blink 能力，走 `VKGS_USB_BREQ_IDENTIFY` 请求。`vcan_usb` 没有对应
  方法（原因同内核侧：固件未实现）。
- `tools/canctl.py` 新增两个子命令：`state`（打印 `bus.state` 和
  `get_berr_counter()`）、`identify on/off`（仅 `vkgs_usb`，对 `vcan_usb`
  执行会给出明确报错而不是崩溃）。见《[Python 终端工具](Python终端工具.md)》
  §9.1/§9.2。
- `vkgs_usb` 的 `CanFrame` 补上了 `timestamp_us` 字段（`vcan_usb` 一直都有）。
  之前即使打开 `MODE_HW_TIMESTAMP`，收到的时间戳字节也只是被跳过、从未读出;
  现在会被正确解析进 `CanFrame.timestamp_us`（`bus.py` 目前默认仍不启用
  硬件时间戳，这是把已死代码补活，不改变默认行为）。

### 2. 稳定性

- `vkgs_usb` 每帧 TX 前后的 `BULK_OUT_READY_S`(5ms)/`CAN_TX_SETTLE_S`(10ms)
  睡眠、以及 `start()`/`stop()` 的 `MODE_TRANSITION_SETTLE_S`(150ms) 睡眠，
  核实后确认是**固件强制的调度延迟**（固件主循环按固定节拍处理 USB 暂存
  FIFO），不是可随意缩短的保守值——缩短并不会变快，只会有和固件竞态的风险。
  这次**没有缩短数值**，改为在代码里明确写清楚这是硬性吞吐上限：稳态 TX
  吞吐上限约为每通道 66 帧/秒，每次 `start()`/`stop()` 循环固定多花约
  300ms。详见《[PythonCAN 使用手册](PythonCAN使用手册.md)》。

### 3. 命名规范

- `HAL_VCAN_USB_BREQ_BSP_DEVICE_INFO` → `VCAN_USB_BREQ_BSP_DEVICE_INFO`，
  `GS_USB_BREQ_GET_BSP_DEVICE_INFO` → `BREQ_BSP_DEVICE_INFO`（与内核端重命名
  保持同步，方便对照协议文档）。
- `vcan_usb` 的 `BREQ_NOMINAL_BITTIMING` 改名为 `BREQ_BITTIMING`，与
  `vkgs_usb` 侧统一。
- `vcan_usb/protocol.py` 里重复出现的魔法数字 `24`（= 8 字节 HEADER + 16
  字节 CAN_FRAME_FIELDS）提成具名常量 `_HEADER_AND_FRAME_FIELDS_SIZE`。
- `vkgs_usb/protocol.py` 新增 `EVENT_HEADER` 结构体常量，用于 STATE/BERR/
  LOAD 事件帧（8 字节：echo_id+channel+reserved+flags），与 CAN 数据/TX
  回显帧用的 `HOST_HEADER`（12 字节：echo_id+can_id+dlc+channel+flags+
  reserved）区分开——这两种帧的字段布局并不相同，此前代码统一用
  `HOST_HEADER` 解析会读到错位的 channel/flags 值（因为从未使用这两个字段
  才没暴露成 bug）。

### 4. 测试/文件组织

- 新增 `tests/_helpers.py`，把原来定义在可执行脚本 `tests/hardware_test.py`
  里的 `_arbitration_id`/`_open_buses`/`_shutdown_buses` 移过去；
  `tests/unit/test_test_helpers.py` 和 `hardware_test.py` 都改成从这个模块
  导入，单元测试不再依赖一个脚本内部的私有函数。`hardware_test.py` 同时兼容
  直接 `python tests/hardware_test.py` 运行（相对导入不可用时回退成绝对
  导入），不影响 `can-test` 包装脚本的现有用法。
- 其余部分（`canctl`/`can-test` 是薄 venv 选择包装，非重复；
  `tests/unit/*` 与 `tests/hardware_test.py` 已经清晰分开）审计确认没问题，
  未改动。
- 未发现遗留调试 `print()`——现有 `print()` 全部在 `tools/canctl.py`（命令行
  工具，打印本来就是预期行为），未改动。

## 三、验证

```bash
# Python：mock 单元测试，不需要硬件
cd python-cli
PYTHONDONTWRITEBYTECODE=1 .venv-linux/bin/python -m unittest discover -s tests/unit -v
# 结果：Ran 26 tests ... OK (skipped=3，3 个是 Windows-only 用例)

# 内核：在本机确认编译通过（有匹配的内核头）
cd kernel/vcan_usb && make && make clean
cd kernel/vkgs_usb && make && make clean
```

**内核驱动的硬件验收测试本环境无法运行**（未接入真实设备）。请在有硬件的机器
上跑：

```bash
sudo /path/to/04.VCANDrive/kernel/tests/vcan_usb/test_vcan_usb.sh
sudo /path/to/04.VCANDrive/kernel/tests/vkgs_usb/test_vkgs_usb.sh
```

除了原有的收发矩阵验证外，这次建议额外确认三项新行为：

1. `ip link set can0 type can berr-reporting on` 之后能成功开启（之前
   `ip -details link show` 的 `berr-reporting` 一直是 off 且无法打开）；
   人为制造总线错误（如断开 CANH/CANL 一根线）时能在 `candump -e` 或
   `ip -details -statistics link show` 里看到 protocol-violation 错误帧。
2. `vkgs_usb` 接口执行 `ethtool -p can0 5` 时设备 LED 会闪烁 5 秒。
3. Python 侧：打开一个 `vcan_usb`/`vkgs_usb` bus 后，故意制造 bus-off/
   error-passive 条件，确认 `bus.state` 从 `BusState.ACTIVE` 变为
   `BusState.PASSIVE`，`bus.get_berr_counter()` 返回的计数在增长。


## 四、文档与术语统一（本轮补充）

为统一用户阅读体验，本轮对文档做了以下不改变驱动行为的说明性更新：

- 全量文档统一 channel、interface、bus/address/port_path 的含义：channel
  指 USB interface 编号；canX 为 Linux 分配的名称；bus/address/port_path 用于
  多设备与多次插拔后的稳定定位。
- 整理命令示例中的路径、前提条件与术语解释，减少“通道”与“接口”语义歧义；
- 对 LICENSE、README 和各子 README 补充“仅文档更新、仅优化说明”的说明；
- 补充若干文档中的小误差（示例字段名、占位路径）以提升可执行性。

本轮修改未改动任何内核/固件代码与 Python 运行时源码，仅改动文档与仓库说明。

# 验收测试路线：从第一帧到完整覆盖

先按[快速入门](快速入门.md)确认模式、驱动、两路接线和第一帧收发。本页用于选择下一档测试；所有总线模式测试都会真实发送 CAN 帧、改变位时序和终端设置，只在隔离测试总线上运行。下面的 Python 命令均在仓库 `python-cli/` 目录执行；`$backend` 取 `vcan_usb` 或 `vkgs_usb`，与设备当前模式一致。

## 先选需要的覆盖范围

| 目标 | 运行项 | 会验证什么 | 仍需另测 |
|---|---|---|---|
| 确认接线和基本收发 | [第一帧](快速入门.md) | 两通道、同位率、真实总线 ACK 与一帧数据 | FD、连续收发、错误恢复 |
| 日常改动后的快速回归 | `functional`，每发送端每阶段 20 帧 | 经典 CAN、FD/BRS 关、FD/BRS 开的双向总线及各通道内部回环；帧数、顺序、载荷和 USB 错误 | 复杂帧矩阵、长期压力和应用协议 |
| 更全面的原始帧与生命周期回归 | `socketcan`，每发送端每阶段至少 100 帧 | 额外覆盖经典/FD 混合矩阵、标准/扩展/RTR、不同位率、定向序号和重复打开；也保留上述六阶段 | ISO-TP、J1939 TP、ECU 周期调度、canfdtest 请求/应答、实测 90% 负载、物理 ESI 注入 |
| 吞吐和缓冲稳定性 | `stress`，按需要提高帧数、窗口和轮数 | 六类双向/回环阶段在更长连续流量下的收发一致性、USB 错误及应用队列溢出 | `socketcan` 混合矩阵和 Linux 专项协议 |
| Linux 内核驱动与总线专项 | [内核验收脚本](#4-linux-内核驱动专项) | 250 kbit/s 混合帧、ECU 流量、ISO-TP/J1939 TP、序号、FD、负载、1 Mbit/s 混合帧及重复打开等 | Python USB 后端；可选工具未安装时会标记跳过 |

`--frames` 是**每个发送端、每个阶段**的帧数，不是整套测试的总帧数。窗口 `--window` 控制待确认的发送批次上限。`--skip-fd` 是明确的经典 CAN 部分覆盖；`TEST PASSED` 只代表本次所选项目通过。

## 1. 快速功能回归

Windows PowerShell：

```powershell
$py = '.\.venv-win\Scripts\python.exe'
$backend = 'vcan_usb'  # GS_CAN 改为 'vkgs_usb'
& $py .\tests\hardware_test.py --interface $backend --channels 2 --mode bus --profile functional --frames 20 --window 1
```

Linux 使用 `sudo ./can-test` 替换前面的 Python 文件入口，并把 `$backend` 换成实际后端名。预期输出包括 `BUS 1/2/3` 和 `LOOPBACK 1/2/3`，每个方向显示 `TX=... RX=... MATCH`、`invalid/duplicate/reorder=0`，末尾为 `TEST PASSED`。如果设备只支持经典 CAN，显式添加 `--skip-fd`，并在验收记录中写明 FD 未覆盖。

## 2. 扩展帧矩阵与重复打开

在同样的双通道接线上运行：

```powershell
& $py .\tests\hardware_test.py --interface $backend --channels 2 --mode bus --profile socketcan --frames 100 --window 32 --reopen-loops 4 --results-json "$env:TEMP\vcandrive-socketcan.json"
```

`socketcan` 是 **Python 测试配置名**，仍通过当前的 USB 后端访问设备，不会加载 Linux SocketCAN 驱动。经典矩阵有 36 种组合，经典/FD 混合矩阵有 100 种；`--frames 100` 至少遍历一次完整混合矩阵。少于 100 帧时脚本会标记矩阵覆盖不足。末尾的 `Coverage gaps versus kernel stress.sh` 是与 Linux 内核专项测试相比仍未覆盖的项目，不能把它误读成全部测试已完成。

Linux 同一路线的命令为 `sudo ./can-test --interface vcan_usb --channels 2 --mode bus --profile socketcan --frames 100 --window 32 --reopen-loops 4`；GS_CAN 设备把接口名改为 `vkgs_usb`。

## 3. 压力与缓冲检查

先用默认规模建立基线，再按目标时长提高帧数；不要把 `functional --window 1` 的速率当作吞吐上限。

```powershell
& $py .\tests\hardware_test.py --interface $backend --channels 2 --mode bus --profile stress --frames 1000 --window 32 --rounds 1
```

需要更长时间时可提高到 `--frames 10000 --rounds 5`。每阶段查看两方向 `MATCH`、`invalid/duplicate/reorder=0`、`app_drop=0`、`overflow=0`，同时记录 `tx_errors/rx_errors` 和控制器状态。USB transfer 次数不是 CAN 帧数；最终结论以已验证的 CAN 帧数和载荷字节数为准。结构化报告可加 `--results-json` 写到仓库外的路径。

## 4. Linux 内核驱动专项

本项仅在 Linux 上运行，使用 `kernel/` 中对应模式的驱动，与上面的 Python USB 测试分开。脚本默认构建/重载驱动、重配接口并启用终端，要求两路 CAN 接在同一条隔离总线上：

```bash
# 在 VCANDrive 仓库根目录，按当前模式只运行其中一个
sudo ./kernel/tests/vcan_usb/test_vcan_usb.sh
sudo ./kernel/tests/vkgs_usb/test_vkgs_usb.sh
```

它依次运行 250 kbit/s 混合帧、ECU 周期/事件/诊断流量、ISO-TP、J1939 TP、序号完整性、FD 往返、目标负载、1 Mbit/s 混合帧、FD 压力和重复打开。默认设置在 `kernel/tests/common/stress.sh`；例如 `DURATION` 控制持续时间，`SEQUENCE_FRAMES` 控制序号帧数，`CANFD_LOOPS` 控制 FD 循环次数，`REOPEN_LOOPS` 控制重开次数。旧的 `NFRAMES` 参数已不使用。

可选工具或 FD 能力不足时，脚本会显示 `SKIP`，最终结果可能是 `STRESS TEST PASSED (partial coverage...)`。只有环境具备全部可选能力且需要严格完整覆盖时，才使用 `REQUIRE_ALL=1` 将跳过项视为失败。先阅读[Linux 驱动安装](Linux内核驱动安装.md)与[SocketCAN 使用手册](SocketCAN使用手册.md)，确认脚本会改动的接口属于测试总线。

## 5. 如何记录和判断结果

记录设备当前 USB 模式、软件版本、两路 CAN 接线与终端、标称/数据位率、命令全文、`TX/RX`、异常计数、跳过项和脚本退出码。Python 测试退出码 0 表示所选阶段通过，1 表示验收失败，2 表示参数或运行错误。任一阶段失败时保留首次异常序号和后续样本，不根据 `RX` 差额直接断言是物理丢帧；还要核对载荷、队列溢出和 CAN 控制器状态。Linux 脚本的 `SKIP` 不等于通过该项目。

业务场景还有单独的验证：DBC 的 encode→decode、CANopen 的对象字典/NMT/SDO/PDO、目标 ECU 周期调度和故障注入，应按[应用开发指南](CANopen与DBC开发指南.md)或设备协议要求测试，不能由原始 CAN 收发结果替代。
